# 设计模式决策报告（baseline-v1）

## 1. 决策总览

| 编号 | 决策 | 备选 | 选择理由 |
|---|---|---|---|
| D1 | 报名规则用**策略模式**（`RegistrationPolicy` + 2 实现） | if/else 判断 `policy_type` | 新增规则不改主流程（OCP）；规则可单测 |
| D2 | 名额检查放**服务层公共规则**（`CapacityChecker`） | 放进策略内部 | 名额是“已通过”的全局不变量，两种策略都要遵守；放策略会重复实现且易不一致 |
| D3 | 报名与通知用**观察者/事件**解耦（`EventBus` + `NotificationObserver`） | 服务里直接写消息表 | 通知失败不能影响报名（R6）；未来加渠道不改业务代码 |
| D4 | 事件在**事务提交后**发布 | 事务内发布 | 避免“消息已写、报名回滚”的假通知 |
| D5 | 通知按 `dedupe_key` **幂等**写入 | 无去重 | 避免重试/重复发布产生重复消息 |
| D6 | 删除有报名的活动→**拒绝删除并提示** | 软删除 | 实现简单、语义清晰；软删除要处理列表过滤与统计口径 |
| D7 | 审批的名额复查与状态更新放**同一事务**（`BEGIN IMMEDIATE`） | 先查后改（两条语句） | 防并发批准导致超额（C8） |

## 2. 策略模式（D1 + D2）

### 结构

```python
class RegistrationPolicy(ABC):
    name: str
    @abstractmethod
    def submit(self, ctx: PolicyContext) -> PolicyResult: ...

class DirectRegistrationPolicy(RegistrationPolicy):  # 名额足→已通过
class ReviewRegistrationPolicy(RegistrationPolicy):  # →待审核
```

`PolicyContext` 携带 `activity / student / capacity_checker / now`；`PolicyResult` 返回 `ok/status/code/message`，**策略不写库**，落库由 `RegistrationService` 统一完成。

### 名额检查为什么不属于策略

这是设计任务 B 要求说明的关键点。理由：

1. **规则性质不同**：`policy_type` 决定的是“提交后的流程”（直接通过 vs 待审核），而“名额按已通过计算、满员不得再通过”是**对活动容量的全局约束**，与流程无关；
2. **两种策略都需要它**：直接报名在提交时检查，审核型在批准时检查；把它放进策略会导致同一规则写两遍，且未来第三种策略还要再写一遍（DRY 被破坏）；
3. **一致性风险**：若某个策略忘了检查，系统会静默超额，而这个错误在业务上不可接受；
4. **可测试性**：`CapacityChecker` 可独立单测；策略只测“流程选择”，职责更单一（SRP）。

因此：**策略决定流程，服务/公共规则保证不变量**。

### 成本

- 多出 1 个接口、2 个实现、1 个注册表（`POLICIES`）与 1 个上下文对象；
- 新增策略需改注册表（一处），但主流程零改动。

### 扩展方式（预埋、不实现）

新增 `WaitlistRegistrationPolicy`（候补）时：实现接口 → 注册 `policy_type='waitlist'` → 页面下拉加一项，`RegistrationService` 无需修改。

## 3. 观察者/事件（D3–D5）

### 结构

- `RegistrationEvent(type, registration, activity, student)`：`submitted / approved / rejected / cancelled`；
- `EventBus.subscribe(event_type, handler)` / `publish(event)`：同步调用，逐个 `try/except`，失败收集后写 `instance/notification_failures.log`；
- `NotificationObserver.handle(event)`：拼中文消息内容，`MessageRepository.add(..., dedupe_key)` 幂等写入。

### 事务边界（R6 的回答）

**先提交报名事务，再发布事件**：

- 报名记录一旦合法提交，就应保留；通知失败属于“副作用失败”，不能反向删除业务数据；
- 失败留痕：日志文件 + 消息未写入（可在后台重放，本版本不做）；
- 若反过来“事务内发通知”，通知写库失败会导致报名回滚——用户看到“报名失败”但其实名额被占用过，语义混乱。

### 去重

`dedupe_key = f"{event.type}:{registration.registration_id}:{status}"`，数据库唯一索引；重复发布时 `INSERT OR IGNORE` 不产生第二条消息。

### 成本

- 多 2 个类 + 1 张事件定义；
- 同步总线意味着通知变慢会拖慢请求（本系统量级可接受）；
- 调试链路变长（日志需记录 event type）。

### 备选比较

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 服务里直接写消息表 | 最简单 | 业务与通知耦合，通知失败处理散落 | 不选 |
| 同步 EventBus（本方案） | 解耦、可扩展、实现轻 | 仍是进程内同步 | **选用** |
| 消息队列 | 真正异步、可重试 | 超出实验范围，运维成本高 | 不选（3.3 明确“无须引入消息队列”） |

## 4. SOLID 对应

| 原则 | 体现 |
|---|---|
| SRP | 仓储只做 SQL；策略只做流程判断；服务只做编排；观察者只做通知 |
| OCP | 新增报名策略/通知渠道不改 `RegistrationService` |
| LSP | 两种策略可互换，返回结构一致 |
| ISP | `RegistrationPolicy` 只有一个方法，订阅者只依赖事件对象 |
| DIP | 服务依赖策略接口与仓储抽象，不直接 new 具体实现（注册表注入） |

## 5. 删除活动策略（D6）

选择“**有报名则拒绝删除并提示**”：

- 报名与消息是审计数据，删除活动会让历史记录悬空；
- 软删除需要额外字段、列表过滤、统计口径调整，成本高于收益；
- 提示文案可直接告诉管理员“该活动已有 N 条报名，无法删除”。

## 6. 预埋扩展点（本版本不实现）

| 扩展点 | 位置 | 未来用途 |
|---|---|---|
| 策略注册表 | `policies.POLICIES` | 候补、邀请制、多级审批 |
| 事件类型 | `events.py` | 新增“活动取消”“名额释放”等事件 |
| 订阅者列表 | `EventBus` | 邮件/短信/站内信多渠道 |
| 名额计算 | `CapacityChecker` | 候补队列、分组配额 |
| 审批动作 | `RegistrationService.approve/reject` | 批量审批、审批备注 |

## 7. 已知成本与风险

1. 分层带来文件数量增加（约 8 个模块），小项目里显得“重”，但为第 2 周变更预留了边界；
2. 同步事件总线在通知量大时会拖慢请求，本系统规模（200 人）可接受；
3. SQLite 并发写能力有限，审批热点场景需依赖事务串行化，压测不在本实验范围。
