## 2. 关键论证

### 2.1 为什么用继承而不是独立实现（D8）

「年级限定直接报名」在语义上等于「直接报名」加一个**前置资格**：名额判断、状态取值、事件发布完全相同，只有「谁有资格提交」不同。

- 继承后 `GradeLimitedPolicy.submit` 只有两步：年级不满足 → 返回拒绝；满足 → `super().submit(ctx)`；
- 容量计算只有一份实现，未来若名额规则变化（如候补），只需改父类；
- 唯一代价是子类依赖父类语义。这是**语义继承**（is-a），不是实现复用，符合里氏替换：凡是「直接报名」成立的地方，年级限定策略都能替换，只是多一个更严格的前置条件。

反例说明：如果做成独立类，需要复制 `has_room` 判断，两处逻辑会在下次名额规则变化时分叉——这正是变更适应评分要规避的。

### 2.2 为什么年级放进 `PolicyContext` 而不是 session（D9）

- session 里的年级是登录时的快照，管理员改库后不刷新，测试也难造数据；
- 策略若直接查库，会把 SQL 带进策略层，破坏「策略只做判断」的边界；
- 由服务查一次 `StudentRepository.get` 再注入，策略保持纯函数式，测试可用内存对象。

服务层这行注入是**装配**，不是业务逻辑：`submit` 的分支、事务、事件顺序均未改动。

### 2.3 迁移为什么要重建表（D10）

SQLite 不支持 `ALTER TABLE ... MODIFY CHECK`。做法：

1. `PRAGMA foreign_keys=OFF`（迁移事务内）；
2. 建 `activities_new`（CHECK 含 `grade_limited`）→ 复制数据 → 删旧表 → 改名；
3. `ALTER TABLE students ADD COLUMN grade ...`（SQLite 允许带 CHECK 与默认值）；
4. 建 `emails`、`schema_version`，写入版本 2；
5. 恢复外键检查。

`SchemaMigrator.current_version/migrate` 幂等：版本已是 2 直接返回，重复启动无副作用。测试覆盖「空库初始化」与「版本 1 旧库升级」两条路径。

### 2.4 邮件为什么先占位（D11）

若「先发送、成功后再写记录」，则发送成功但写记录失败会产生重复发送窗口；并发下两个观察者也可能同时发送。先 `INSERT OR IGNORE` 占位：

- 占位失败（0 行）→ 说明该事件已处理，直接跳过；
- 占位成功 → 发送 → 更新 `status` 为 `已发送` 或 `失败`。

副作用是「占位成功但进程崩溃」会留下 `待发送` 记录，属于可审计的不一致，比重复发邮件更可接受。

### 2.5 失败隔离的边界（D12）

- `EmailNotifier.handle` 内部 `try/except Exception`，记录失败后吞掉异常；
- `EventBus` 仍保留 `_log_failure`，作为观察者之外的兜底；
- 报名事务在事件发布前已提交，异常无法回滚业务——这是 baseline 已确定的顺序，v2 不改变。
