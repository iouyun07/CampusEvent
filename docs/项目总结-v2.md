# CampusEvent 项目总结（change-v2）

## 1. 项目概况

CampusEvent 是一个面向校园场景的活动报名与管理系统，单机运行、无需登录，学生端通过页面切换演示身份，管理端固定开放。技术栈为 Python 3.13 + Flask 3.1.3 + Jinja2 服务端渲染 + SQLite（标准库 `sqlite3`），不使用前端框架与 JavaScript 依赖，数据保存在 `instance/campus_event.db`。

项目按实验要求分为两版：

- **baseline-v1**：实现 P2-F01～P2-F08 全部初始功能，19 条自动化测试，部署到 PythonAnywhere；
- **change-v2**：在需求变更（CR-01 年级限定报名、CR-02 模拟邮件通知）发布后增量实现，30 条测试，未重新部署线上。

## 2. 需求理解

初始需求共 8 项功能（活动浏览、报名、名额控制、审批、取消报名、我的报名、消息通知、活动管理）与 7 条业务规则。其中最容易出错的三条是：

1. **名额只统计「已通过」**：待审核不占名额，因此报名阶段与审批阶段都要检查容量；
2. **同一活动同一学生只能有一条有效报名**：已取消、已拒绝的记录要保留，不能被误判为「重复报名」；
3. **活动开始后禁止报名**：以服务器时间与活动开始时间比较，字符串格式统一为 `YYYY-MM-DD HH:MM`。

这些规则被分别落在数据库约束（部分唯一索引）、领域方法（`Activity.has_started`、`Registration.is_active`）与服务层事务中，而不是散落在模板里。

## 3. 架构与关键设计

### 3.1 分层

```
views（路由/表单） → services（事务与应用逻辑） → repositories（SQL）
                          ↘ policies / capacity（规则）
                          ↘ events → notifications（通知）
```

- **策略模式**：`RegistrationPolicy` 抽象接口，`DirectRegistrationPolicy` 与 `ReviewRegistrationPolicy` 分别处理「直接通过」与「进入待审核」；活动通过 `policy_type` 选择，注册表 `POLICIES` 集中管理。
- **观察者模式**：`EventBus` 发布 `RegistrationEvent`，`NotificationObserver` 写站内消息；业务事务提交后才发布事件，通知失败只写日志，不回滚报名。
- **事务边界**：审批使用 `BEGIN IMMEDIATE`，在事务内重新读取报名与已通过人数再决定是否通过，避免「先查后改」造成的超卖。
- **幂等**：站内消息与邮件均有 `dedupe_key` 唯一约束；邮件采用「先占位再发送」，重复事件直接跳过。

### 3.2 变更的扩展点

baseline 阶段有意预留了三个扩展点：策略注册表、事件总线、迁移钩子。change-v2 的落地验证了它们的价值：

- 新增 `GradeLimitedPolicy` 继承直接报名策略，先判年级再复用父类的名额检查，**容量逻辑仍只有一处实现**；
- 新增 `EmailNotifier` 订阅同一批事件，**事件总线与站内消息观察者未改动**；
- 新增 `migrations.migrate`，启动时自动把旧库升级到 v2，**没有删库重建**。

## 4. 需求变更的应对

| CR | 关键点 | 实现方式 | 核心流程改动 |
|---|---|---|---|
| CR-01 年级限定 | 仅大二、大三可报名，其他年级给明确原因；名额规则不变 | 新增 1 个策略类 + `students.grade` + 上下文注入 | `submit` 仅新增 1 处传参 |
| CR-02 模拟邮件 | 通过/审核通过/拒绝时发邮件；失败不回滚；不重复 | 新增 `emails` 表、`EmailNotifier`、`MockEmailSender` | 无 |

度量结果：新增类 6 个（上限 7）、修改核心类 1 个且业务逻辑零改动、回归失败 0、测试 19→30、变更耗时约 8 分钟。详细数据见《变更影响分析-v2》。

## 6. 测试与验收

共 30 条用例，分三层：

1. **验收用例**：C1–C10 全部覆盖，含名额满、重复报名、审批并发复查、取消后统计、重启持久；
2. **变更用例**：CR1-01～05、CR2-01～04，覆盖年级判定、拒绝提示、容量复用、双渠道通知、失败隔离、重复事件；
3. **迁移用例**：旧库升级与幂等执行。

执行命令 `.venv\Scripts\python.exe -m pytest -q`，结果 `30 passed`，0 失败。除自动测试外，用临时库启动真实应用做了路由冒烟，并在 PythonAnywhere 线上完成人工走查。

## 7. 遇到的问题与解决

1. **SQLite 无法修改 CHECK 约束**：`policy_type` 需要新增取值，`ALTER TABLE` 不可行。解决办法是事务内重建 `activities` 表（关闭外键、复制数据、改名），并用 `schema_version` 保证只执行一次。
2. **迁移必须兼容旧库**：直接改 `schema.sql` 只对新库生效。补充了 v1 结构脚本与升级用例，验证旧数据（活动、报名）在升级后不丢失、外键完整。
3. **邮件失败不能影响报名**：如果发送放在事务里，异常会回滚报名。改为事务提交后由观察者发送，观察者内部捕获异常并写 `notification_failures.log`。
4. **重复事件导致重复通知**：仅靠「先查再插」有并发窗口。改为 `dedupe_key` 唯一 + `INSERT OR IGNORE`，返回 0 即跳过。
5. **模板拿到的是原始策略值**：新增策略后页面显示 `grade_limited` 而不是中文。通过 `app_context_processor` 注入 `policy_labels` 统一解决。
6. **开发环境限制**：本机沙箱对临时目录权限敏感，pytest 与 pip 需要额外的临时目录补丁；这类问题与业务无关，但会阻塞测试，已记录在 AI 开发日志。

## 8. 不足与改进

- 年级规则固定为大二、大三，未做后台配置；若后续变更频繁，可改为活动维度的规则表。
- 邮件为模拟实现，未接入真实 SMTP；接入时需要补充重试与退避策略。
- 无登录鉴权，学生身份靠页面切换，仅适合课程演示。
- SQLite 不支持多实例并发，生产化需要迁移到 PostgreSQL 并使用行级锁或乐观锁。
- 未实现分页与活动搜索的高级筛选，数据量增大后需要补充。

## 9. 结论

本项目以「稳定核心 + 扩展点」的方式完成了从 baseline-v1 到 change-v2 的演进：新增两条 CR 只带来 6 个新类与 1 处数据注入，核心报名/审批流程零逻辑改动，19 条既有回归全部通过。设计与实现的取舍均有文档记录，变更的可维护性指标（新增类数、核心类修改数、回归失败数、耗时）可复核。
