## 3. 设计取舍要点复核

1. **为什么用策略模式**：报名规则是变化点（直接/审核，未来可能候补），用接口隔离变化，主流程只依赖抽象；
2. **增加了什么成本**：多一个接口与注册表、类数量增加、调试链路变长；
3. **未来如何扩展**：新增策略只改注册表；通知渠道新增订阅者；通知失败可后台重放。

## 4. 评审发现的问题与处理

| # | 问题 | 处理 |
|---|---|---|
| 1 | 名额检查放策略还是服务，初稿有分歧 | 定为服务层公共服务（`CapacityChecker`），理由写入决策报告第 2 节 |
| 2 | 通知在事务内还是事务后发布 | 定为提交后发布，失败只留痕，理由写入决策报告第 3 节 |
| 3 | 删除活动采用拒绝还是软删除 | 定为拒绝删除并提示（D6） |
| 4 | 审批并发下名额复查的顺序 | 定为 `BEGIN IMMEDIATE` 事务内“查状态→查名额→更新”（D7） |

## 5. 结论

设计材料通过自评审，边界情况（超员、重复报名、取消、审批冲突、通知失败、重启持久化）均已在设计与用例中覆盖，**可以进入编码实现阶段**。
