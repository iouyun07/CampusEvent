# 初始 SRS 分析（CampusEvent baseline-v1）

> 依据：《实验二》3.2 初始业务需求、附录 B（B.1 领域数据与角色、B.2 业务规则、B.3 设计检查表）。
> 本文只做分析与拆解，不包含实现。

## 1. 项目目标与范围

校园管理员发布活动，学生浏览并报名；排名结果通过站内消息通知。初始版本支持两类报名方式：

- **直接报名**：提交即通过（名额足够时）；
- **审核型报名**：提交后进入“待审核”，由管理员批准或拒绝。

范围外（明确不做）：用户注册、复杂权限系统、消息队列、站内消息推送渠道（邮件/短信）、活动签到、支付。

## 2. 角色

| 角色 | 说明 | 演示方式 |
|---|---|---|
| Student | 浏览活动、报名/取消、查看站内消息 | 固定演示账号（如 `2024001` 张三） |
| Admin | 创建/编辑/删除活动、审批报名、查看统计 | 固定管理员账号 |

无需注册与密码体系，登录页选择演示身份即可。

## 3. 领域对象

| 对象 | 主要字段 | 约束 |
|---|---|---|
| Student | student_id、name | student_id 唯一 |
| Activity | activity_id、title、category、start_at、location、capacity、policy_type | capacity 为正整数；活动开始前允许报名 |
| Registration | registration_id、activity_id、student_id、status、created_at、updated_at | status ∈ {待审核, 已通过, 已拒绝, 已取消} |
| Message | message_id、student_id、activity_id、content、created_at、is_read | 报名/审核动作可产生消息 |

## 4. 功能需求拆解

| 编号 | 需求 | 实现要点 |
|---|---|---|
| P2-F01 | 活动管理 | 管理员增删改查；名称/类型/时间/地点/容量/报名方式；容量校验 |
| P2-F02 | 活动查看 | 列表 + 详情；按名称筛选（包含匹配） |
| P2-F03 | 报名/取消 | 提交、取消；同一活动禁止重复有效报名（待审核/已通过） |
| P2-F04 | 报名策略 | 直接报名→已通过；审核型→待审核；由策略对象决定 |
| P2-F05 | 审批 | 批准/拒绝待审核；批准时**再次**检查名额 |
| P2-F06 | 状态管理 | 四种状态与合法迁移：待审核→已通过/已拒绝/已取消；已通过→已取消 |
| P2-F07 | 站内通知 | 报名结果、审核结果写入消息表 |
| P2-F08 | 统计 | 每活动：已通过数、待审核数、剩余名额 = capacity − 已通过数 |

## 5. 业务规则与落点

| 规则（B.2） | 落点 |
|---|---|
| R1 直接报名：名额足→已通过并通知 | `DirectRegistrationPolicy` + `RegistrationService` |
| R2 审核型：提交→待审核；批准时复查名额 | `ReviewRegistrationPolicy` + `approve()` |
| R3 名额按“已通过”计；待审核不占；满员不得再批准 | `CapacityChecker`（服务层公共规则） |
| R4 同一学生同一活动不得有两条有效报名；取消/拒绝保留历史可再报 | 部分唯一索引 `WHERE status IN ('待审核','已通过')` + 服务层校验 |
| R5 可取消待审核/已通过；活动开始后禁止新增报名 | `cancel()` / `submit()` 时间校验 |
| R6 通知失败留痕，不得让报名记录消失 | 事件发布与报名事务分离；失败写日志 |
| R7 持久化；删除有报名的活动采用“拒绝删除并提示” | SQLite 文件；`delete()` 检查报名数 |

## 6. 验收用例映射（C1–C10）

| 用例 | 场景 | 对应实现 |
|---|---|---|
| C1 | 管理员建直接报名活动（容量 2） | `POST /admin/activities/new` |
| C2 | 学生 A 报名直接报名活动 | `submit()` → 已通过 + 消息 |
| C3 | A 重复报名同一活动 | R4 拦截 |
| C4 | B 报名后满员，C 再报失败 | 容量检查 |
| C5 | 审核型活动 A 申请 | 待审核 |
| C6 | 管理员批准 A | 已通过 + 消息 |
| C7 | 管理员拒绝另一申请 | 已拒绝 + 消息 |
| C8 | 批准时容量已满 | 批准失败，不超上限 |
| C9 | 学生取消报名 | 已取消，统计同步 |
| C10 | 重启服务后查询 | 数据持久化 |

## 7. 非功能与约束

- 单机部署，SQLite 单文件；数据与代码分离（`instance/`）；
- 中文界面与错误提示；
- 关键业务规则必须有自动化测试（pytest）；
- 部署到云服务器（PaaS），README 给出访问地址；
- 设计先行：类图、时序图、模式决策在编码前完成并自评审。

## 8. 风险与待确认

1. 删除活动的策略二选一：本版本采用“有报名则拒绝删除”，理由见设计决策；
2. 并发批准的名额竞争：SQLite 写事务串行化 + 事务内复查；
3. 活动开始时间用本地时区文本（`YYYY-MM-DD HH:MM`），不处理跨时区；
4. 站内消息只读列表，不实现消息推送与已读回执的复杂交互。
