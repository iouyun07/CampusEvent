# 变更需求分析（v2）

> 对应教师材料 CR-01（年级限定报名）与 CR-02（模拟邮件通知）。
> 基线版本：`baseline-v1`（tag，2026-11-25 部署于 PythonAnywhere）。
> 本文档只做分析与设计约束，不含代码实现。

## 1. 变更来源与约束

| 项 | 内容 |
|---|---|
| 变更来源 | 教师发布的 CR-01、CR-02（baseline-v1 验收通过后发布） |
| 生效版本 | change-v2（新标签，不覆盖 baseline-v1） |
| 部署约束 | 本次不重新部署线上站点；线上保持 baseline-v1 |
| 兼容约束 | 原有 direct / review 两种报名规则行为不得改变 |
| 核心约束 | 不把年级判断、邮件发送写进 `RegistrationService` 的报名/审批逻辑 |

## 2. CR-01：年级限定报名

### 2.1 需求要点

1. 活动新增一种报名规则「年级限定直接报名」，语义与「直接报名」一致（有名额即通过），但增加年级门槛；
2. 学生新增年级字段，取值 1–4（大一至大四）；
3. 仅大二（2）、大三（3）可以报名；其他年级提交时给出明确原因；
4. 名额、活动开始时间、重复报名等原有约束继续生效；
5. 原有 direct / review 行为不变。

### 2.2 验收用例（来自 CR 材料）

| 编号 | 场景 | 期望 |
|---|---|---|
| CR1-01 | 大二学生报名年级限定活动 | 报名成功，状态「已通过」 |
| CR1-02 | 大三学生报名年级限定活动 | 报名成功 |
| CR1-03 | 大一学生报名 | 拒绝并显示原因 |
| CR1-04 | 大四学生报名 | 拒绝并显示原因 |
| CR1-05 | 重跑 C1–C10 | 全部通过 |

### 2.3 现状差距

| 位置 | 现状 | 差距 |
|---|---|---|
| `schema.sql:3-6` | `students(student_id, name)` | 缺 grade |
| `schema.sql:8-16` | `policy_type CHECK IN ('direct','review')` | 缺新规则取值 |
| `campus/models.py:24-28` | `Student(student_id, name)` | 缺 grade |
| `campus/models.py:13-15` | `POLICY_DIRECT / POLICY_REVIEW / POLICY_LABELS` | 缺新常量与中文标签 |
| `campus/policies.py:24-28` | `PolicyContext(activity, student_id, checker)` | 策略拿不到学生年级 |
| `campus/services.py:74` | `PolicyContext(activity, student_id, self.checker)` | 同上，且服务没有学生仓储 |
| `campus/services.py:70-72` | 按 `policy_type` 取策略 | 未注册新策略 |
| `campus/services.py:210` | `policy_type not in POLICY_LABELS` | 校验会拒绝新取值 |
| `app.py:13-23` | 种子学生无年级、无年级限定活动 | 演示与测试缺数据 |

### 2.4 设计选项

| 方案 | 做法 | 新增类 | 修改核心服务 | 评价 |
|---|---|---|---|---|
| A 独立实现 | 新策略类重写「年级判断 + 名额检查 + 返回结果」 | 1 | 0 | 名额计算逻辑重复，违反「名额检查归属统一」 |
| **B 继承直接报名** | `GradeLimitedPolicy(DirectRegistrationPolicy)`：先判断年级，通过则复用父类 | 1 | 1 行（传 student） | 复用容量逻辑，语义上是「直接报名 + 前置资格」，改动最小 |
| C 可组合规则 | 抽 `Rule` 接口，把年级、名额做成规则链 | 3–4 | 中等 | 过度设计，与「尽量不改核心流程」冲突 |

**选择 B**，理由：

1. 年级限定在语义上就是「直接报名的子集 + 资格前置」，用继承表达「is-a」关系是准确的；
2. 容量检查、落库、事务、事件发布全部复用，新增代码只包含「年级判断」这一处变化；
3. 唯一的服务层改动是把 `Student` 传入 `PolicyContext`——这是**数据注入**，不是逻辑修改；策略需要什么数据，由服务提供，符合依赖方向。

**对「是否违反开闭原则」的回应**：核心流程（名额计算、重复判断、事务、事件）零改动；新增策略类属于扩展；注册表与服务构造属于装配。OCP 检验的是「增加一个新规则是否需要改动既有业务逻辑」，答案为否。

### 2.5 影响面

| 文件 | 改动 |
|---|---|
| `campus/policies.py` | 新增 `GradeLimitedPolicy`；`PolicyContext` 增加 `student` 字段；注册进 `POLICIES` |
| `campus/models.py` | `Student.grade`；`POLICY_GRADE` 与标签 |
| `campus/services.py:74` | 传入 `student`（1 行） |
| `campus/services.py:210` | 标签校验自动放行（常量加入 `POLICY_LABELS`） |
| `campus/repositories.py` | 新增 `StudentRepository.get`（读年级） |

| `campus/views.py:143` | 策略标签自动显示「年级限定」，无需改动 |

## 3. CR-02：模拟邮件通知

### 3.1 需求要点

1. 在站内消息之外，新增模拟邮件通知（不接真实 SMTP）；
2. 触发事件：报名通过、审核通过、审核拒绝；
3. 邮件需记录：收件人、主题、内容、发送状态、时间；
4. 发送失败必须记录错误，但**不得回滚报名**，也不得影响主流程；
5. 同一业务事件不得重复发送；
6. 新增订阅者即可，不把邮件代码写进 `RegistrationService`。

### 3.2 验收用例

| 编号 | 场景 | 期望 |
|---|---|---|
| CR2-01 | 直接报名通过 | 站内消息与邮件记录都存在 |
| CR2-02 | 审核批准 / 拒绝 | 两种渠道结果一致 |
| CR2-03 | 邮件发送失败 | 报名状态正确，错误有记录 |
| CR2-04 | 重复提交同一业务动作 | 不重复发送 |
| CR2-05 | 重跑 C1–C10 | 全部通过 |

### 3.3 现状与契合点

baseline-v1 已经预留了观察者结构：

- `campus/events.py` 的 `EventBus` 支持多订阅者（`subscribe('*', handler)`）；
- 事件在事务提交后发布（`services.py:78-92`），失败不会回滚业务；
- `campus/notifications.py` 的 `NotificationObserver` 已经把「事件 → 站内消息」做成独立订阅者。

因此 CR-02 只需要**再加一个订阅者**，`EventBus`、`RegistrationService` 不改。

### 3.4 设计要点

| 关注点 | 方案 |
|---|---|
| 订阅范围 | `EVENT_APPROVED`、`EVENT_REJECTED`（待审核不通知；取消不在本次范围） |
| 幂等键 | `dedupe_key = "email:{事件类型}:{registration_id}:{状态}"`，`emails.dedupe_key` 建 UNIQUE |
| 先占位后发送 | 先 `INSERT OR IGNORE` 占位（得到是否新增），新增才真正「发送」；发送失败更新该行 `status='失败'`、`error=原因` |
| 失败处理 | `EmailNotifier.handle` 内部 try/except：记录失败并写失败日志，不向上抛；报名事务已提交，不受影响 |
| 发送器 | `MockEmailSender`（记录式发送器），可配置 `fail_for` 学生集合用于演示/测试失败路径 |
| 记录位置 | `emails` 表（SQLite），同时可选追加 `instance/email_failures.log` |

### 3.5 影响面

| 文件 | 改动 |
|---|---|
| `schema.sql` | 新增 `emails` 表（含 UNIQUE dedupe_key） |
| `campus/mock_email.py`（新增） | `MockEmailSender.send(...)`，支持失败注入 |
| `campus/notifications.py` | 新增 `EmailNotifier`（订阅 approved/rejected） |
| `campus/repositories.py` | 新增 `EmailRepository`（add/update_status/list_by_student） |
| `campus/views.py:55-70` | `_ctx()` 多注册一个观察者（1 行） |
| `app.py` | 迁移时建表；种子不变 |

## 4. 数据模型变更与迁移

### 4.1 变更内容

| 对象 | 变更 |
|---|---|
| `students` | 新增 `grade INTEGER NOT NULL DEFAULT 1 CHECK (grade BETWEEN 1 AND 4)` |
| `activities.policy_type` | CHECK 增加 `'grade_limited'`（SQLite 不能 ALTER CHECK，需重建表） |
| `emails`（新增） | `email_id`、`student_id`、`activity_id`、`registration_id`、`to_addr`、`subject`、`body`、`status`、`error`、`dedupe_key UNIQUE`、`created_at` |
| `schema_version`（新增） | `version INTEGER`，记录当前结构版本 |

### 4.2 迁移策略

1. **幂等**：`schema_version` 记录版本；已到 2 则跳过；
2. **保留数据**：不删库。activities 采用「建新表 → 复制 → 删旧表 → 改名」，students 用 `ALTER TABLE ADD COLUMN`（SQLite 允许带 CHECK 的加列）；
3. **新库**：`schema.sql` 直接是 v2 结构，初始化时写入版本 2；
4. **旧库**：baseline 部署过的库（版本 1）首次启动自动迁移到 2；
5. **测试覆盖**：迁移需分别验证「空库」与「版本 1 旧库」两条路径。

## 5. 非功能与风险

| 项 | 说明 |
|---|---|
| 性能 | 200 条任务规模不变；emails 表按 `student_id` 建索引，量级可忽略 |
| 安全 | 不引入真实邮件凭据；收件人使用演示学号构造的占位地址 |
| 风险 1 | 重建 activities 表时外键引用需在事务内处理（先关外键检查或按顺序重建） |
| 风险 2 | 迁移脚本必须幂等，否则每次启动都会重建表 |
| 风险 3 | 邮件失败注入不能影响真实场景：默认关闭，仅测试/演示显式开启 |
| 风险 4 | 线上不部署本次变更，README 需注明线上为 baseline-v1 |

## 6. 范围边界（本次不做）

- 不重新部署线上站点（教师要求：网站不用改）；
- 不接真实 SMTP、不做邮件重试队列、不做邮件模板引擎；
- 不新增页面与路由；年级限定活动的展示复用现有策略标签；
- 不改 `RegistrationService.submit/approve/reject/cancel` 的业务逻辑。
